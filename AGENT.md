# AGENT.md — RAG_notes

Guidance for any AI agent (OpenCode, Claude, or other) working in this repository.

## What this project is

A personal RAG-based AI agent for querying, navigating, and — eventually — editing
Vladyslav's own Obsidian markdown study notes through a conversational interface.

## Core value: this project exists to build understanding, not just to ship

The primary success criterion is a working codebase Vladyslav genuinely understands —
not the fastest path to a finished feature. This shapes how an agent should behave here:

- **Don't hand over finished solutions.** Work step by step, propose approaches, explain
  trade-offs, and let Vladyslav write the implementation himself.
- **Exception:** repetitive, read-only boilerplate (e.g. another simple read-only tool
  following an existing pattern) can be generated directly — it doesn't teach anything
  new to write by hand.
- **Answer "why", not just "how".** Vladyslav asks conceptual questions alongside
  implementation ones (e.g. why JSON Schema acts as a contract, how `**kwargs`
  unpacking works, how the `messages` history mechanic works) — treat those as part of
  the task, not a detour from it.
- **Debug live, iteratively.** Prefer walking through a bug together over dumping a fix.
- Vladyslav describes himself as a Strong Junior — assume solid fundamentals, don't
  over-explain basics, but don't skip the reasoning either.

## Hard engineering contracts

These are settled decisions — don't relitigate them without a real reason:

1. **Every tool returns `str`.** Returning rich objects (e.g. a LlamaIndex `Response`)
   breaks JSON serialization in the agent loop. This already caused one real bug
   (`TypeError: Object of type Response is not JSON serializable`); the fix was
   returning `str(response)` explicitly. Keep returning `str` everywhere.
2. **Separation of concerns:** `src/rag/` has no knowledge of tool-calling. The agent
   layer calls into RAG, never the reverse.
3. **Registry over conditionals:** tool dispatch goes through the `TOOLS` dict in
   `src/tool/registry.py`, not `if/elif` chains.
4. **No premature abstraction.** LangGraph, write tools, and multi-modal RAG are
   deferred on purpose (see Roadmap) — don't introduce them speculatively.
5. **No Claude Pro API / account-sharing services** as an LLM backend for this project.
   The agent layer uses the `openai`-compatible SDK pointed at OpenRouter, chosen
   deliberately for model flexibility and cost control — not the `anthropic` SDK.

## Repository structure

Detailed, up-to-date per-directory documentation is generated by the **cartography**
skill: each directory has its own `codemap.md`, and there's a root codemap acting as
the repository atlas. **Read those for implementation-level detail** (responsibilities,
data flow, integration points per module) — this file intentionally stays high-level
and doesn't duplicate them. Re-run cartography after structural changes so the maps
stay accurate.

## Stack (settled — don't change without discussion)

- Retrieval: LlamaIndex + Qdrant (Docker), `baai/bge-m3` embeddings via OpenRouter
- Generation: Gemini 2.5 Flash via OpenRouter
- Agent layer: `openai`-compatible SDK pointed at OpenRouter
- Package manager: `uv`
- Dev environment: Nix (`flake.nix`)

## Roadmap / deliberately deferred

- Migrate `search_notes` from "Variant B" (`query_engine.query()`, full answer) to
  "Variant A" (`as_retriever()`, raw chunks) — planned next step
- Write tools: on hold until a diff-preview / confirmation layer exists, to avoid
  unsafe edits to real notes
- LangGraph: not adopted yet — revisit once branching logic, human-in-the-loop
  confirmation, or multi-model pipelines are genuinely needed
- Possible MCP server wrapper, so the RAG system is reusable as a tool by other
  agents — under consideration as a way to give the project a life beyond coursework
- ColPali, for retrieval over slide-deck images from coursework — under consideration
- A storage/retrieval approach for Obsidian `.canvas` files — not yet solved
